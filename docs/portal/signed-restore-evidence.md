# Offline signed synthetic recovery evidence

The recovery topology and registry-custody checks do not prove that a
Postgres/MinIO restore has succeeded. The additional read-only
scripts/portal_restore_evidence.py authenticates a *signed synthetic restore
claim* without contacting Docker, the database, object storage, or fleet hosts.

## Strict evidence contract

The evidence JSON is scoped to synthetic_isolated_restore in staging, with
project kipnerter-staging, a 40-character immutable release SHA, a topology
SHA-256, a unique fixture nonce and a timezone-aware observation date within
24 hours (maximum five minutes into the future).

It must contain exactly two approved digest-pinned PostGIS and MinIO image
references, associated with separate staging-only named volumes. The
database receipt contains a backup SHA-256 and nonzero byte size, and matching
before/after logical hashes, schema hashes and row counts. The object
receipt records backup identity and matching before/after inventory hashes
and object counts.

The claim must say that fixture writers were quiesced, restoration occurred
into new volumes, and truncated Postgres backups and tampered objects were
rejected. Every one of these values is signed, and unexpected or duplicate
JSON fields fail closed.

Two **different** Ed25519 public keys must sign the *identical canonical
receipt payload* (everything except signatures) in separate executor and
independent_reviewer roles. The verifier reads the public keys from a
separately supplied, owner-controlled external trust-root JSON file, never
from the evidence itself. Each key is pinned by its DER SubjectPublicKeyInfo
SHA-256, and both signatures are verified with OpenSSL. No private keys are
needed by, stored in, or generated by the production verifier.

A future invocation, after real independent observers prepare a receipt:

    python3 scripts/portal_restore_evidence.py \
      --evidence /private/restore/receipt.json \
      --external-trust-root /private/custodian/roles.json \
      --expected-release-sha <40-lowercase-hex> \
      --expected-topology-sha256 <64-lowercase-hex>

The trust-root file must be a regular user-owned mode-0600 file, not a
symlink. Its strict JSON schema is version=1,
scope=staging_synthetic_restore, and roles={executor, independent_reviewer}.
Each role has key_id (lowercase DER SPKI SHA-256) and public_key_pem.
Never commit the trust root or its private signing keys to GitHub.

## What verification DOES NOT establish

- Real execution of Postgres/MinIO backup or restore operations. Signed
  declarations may be false; the verifier reads no backup bytes.
- Separate administrative custody of the two private keys. Two distinct
  keypairs can still be controlled by the same person or fleet machine.
- Replay-resistant authoritative checkpoints. A nonce and bounded timestamp
  do not replace a durable externally controlled high-water mark.
- Actual image compatibility, restored schema migration safety, production
  recovery, real tsidp browser acceptance, or permission to cut over services.

A valid verification result therefore ALWAYS reports false for independent
operation observation, administrative key custody verification, rollback
replay protection, and production recovery approval. A valid cryptographic
receipt is useful but is NOT an authorization to set protected release SHA
secrets or change any production system.

The isolated unit tests create disposable Ed25519 keys and synthetic claims
only. They check forged signatures, changed release/topology bindings, wrong
volumes, missing role signatures, stale receipts, mismatched restore hashes,
false negative-control claims, duplicate JSON keys, and unsafe trust roots.
No real backup, object inventory, image load or restore was attempted.
